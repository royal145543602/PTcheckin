# PRIMETIME Check-in：每日名单与报名 UI/UX 完整设计规划

日期：2026-10-12。状态：设计提案；页面、动效和流程尚未接入线上网站。业务规则沿用 daily-roster-booking-plan.md 中已确认的需求。

## 1. 产品目标与设计判断

员工在场馆、移动途中或办公电脑前安排课程和审批报名；客人在手机上快速报名；现场人员用手机或平板完成签到。成功标准是：员工能清楚知道某天谁会来、哪些报名等确认，客人能明确知道自己的申请是否获批。

默认支持一天多个场次，也支持一天只有一份名单；员工端兼顾手机和电脑。设备使用偏好尚待用户回答，视觉提案暂以兼容两者为目标。

丰富感来自明确的层次、不同任务使用不同布局、细致的反馈和连续的操作，而非堆叠装饰。保留现有 PT 深绿和荧光绿品牌，管理界面以浅底便于在场馆明亮环境阅读。

## 2. 功能范围

第一阶段完成每日场次、正式名单、固定客户重复安排、公开报名、后台确认、报名查询、现场签到和历史。

付款状态由员工手动标记；不把批准报名当成付款成功。第一阶段不接在线收款，不自动发送未配置渠道的短信或 WhatsApp 信息。

私人训练默认只有后台安排，员工可以单独决定是否开放报名。团体训练可设置人数上限和报名截止时间。

## 3. 信息架构与导航

### 员工端

- **每日名单**：默认今天；可切换明天、日期和场次。查看正式名单、处理当日待确认报名、打开现场签到。
- **报名**：跨日期的待确认申请、候补、改期与取消申请；待处理数量作为导航角标。
- **客户与安排**：客户档案、付款标签、固定重复安排、未来参与场次。
- **历史**：按日期和客户查看名单、到场情况与操作记录。

电脑采用四项侧边导航；手机采用同样四项底部导航。签到页面是独立现场模式，不挤入复杂后台。管理动作仍由服务器验证，解锁五分钟；名单浏览和写入权限应分别设计，不能让密码到期打断公开签到。

### 客人端

报名链接 → 选择日期／场次 → 填写资料 → 核对提交 → 等待确认 → 查询结果。

查询链接只对应自己的报名；公开链接不显示完整客户名册、电话、付款资料或签名。

报名入口建议使用长期可分享的链接，默认展示明天可报名场次，员工不必每天重新发链接。个人结果链接对应一份申请；现场签到链接对应一个场次，结束后提示该场次已结束。员工可以关闭公开报名或更新分享链接。

### 现场端

对应场次链接 → 当前正式名单 → 选择本人 → 确认签到／签退 → 签名（按课程设置）→ 明确成功结果。

未经后台确认的报名不能进入签到名单。公开链接允许签到，不允许创建场次、增删客户或删除记录。

## 4. 两种视觉方向

### A：当天工作台（推荐主界面）

打开就看到日期、场次、正式名单与待确认报名。电脑左侧为名单，右侧为当日审批；手机使用“名单／待确认”两个页签，避免把所有内容塞在同一屏。

优势是高频操作更直接，适合前台和教练快速处理当天事务。周日期条提供跨日切换；详细月历按需打开。

### B：一周排期台（推荐作为可切换的排期视图）

先看一周课程，选择某场后在下方打开名单与申请。电脑展示周历；手机切换为逐日议程，不缩小七列日历。

优势是提前安排固定客户、私人课程和教练时间更直观。与 A 共用同一批场次和名单，不维护两套数据。

建议正式产品使用 A 作为默认入口，B 作为“周排期”视图；两张视觉图用于确认层级和布局方向，不代表最终文字或数据。

GitHub 参考的应用分工：Cal.diy 的预约确认状态用于客人结果页与审批；Easy!Appointments 的预约管理用于日期／场次组织；LibreBooking 的重复安排与例外用于固定客户排期。项目链接与核实依据见 daily-roster-booking-plan.md。

## 5. 逐页设计

### 5.1 每日名单 / 当天工作台

优先顺序：今天是哪一天 → 哪个场次 → 正式人数与待确认数量 → 名单 → 具体操作。

顶部保留 PT 标识、日期和管理状态；日期条显示星期与日期，支持今天、明天、日历。选择后的完整日期始终可见，不能只显示“明天”。场次条显示名称、时间、教练、地点和人数。

名单使用行列表：头像缩写、姓名、来源（固定安排／后台加入／报名获批）、到场状态。付款标签只在管理详情中展示，不能公开出现在现场大屏。

主操作为“加入名单”；次操作为“分享报名链接”和“打开现场签到”。删除或取消不作为每行最醒目的按钮。待确认面板显示对应场次的申请；批准后该行退出待处理区域，名单人数同步更新。

没有场次时显示“这一天还未安排课程”，提供建立场次和复制其他日期。已建立但无人时提示从客户库加入或分享报名链接。

### 5.2 建立场次与单日调整

采用分组表单：基本资料（日期、时间、课程、教练、地点）→ 名单与名额 → 报名设置。私人课默认不公开，公开开关必须明确。

保存前展示摘要。复制场次可以选择“仅复制课程设置”或“同时复制名单”。改期时列出受影响人数，已签到的场次不能直接挪到另一日期。

### 5.3 待确认报名

列表按日期和场次分组；筛选包括待确认、候补、改期、取消、已处理。默认突出最需要处理的申请，而不是展示所有历史。

行内展示姓名、场次、提交时间和短备注；查看详情后才显示完整联系方式。详情在电脑右侧面板、手机底部抽屉打开，背景名单位置保留。

主要操作“批准”；其他操作“候补、改期、拒绝”。满额时不显示可直接成功的批准按钮，提供候补。批量批准只允许明确选定的申请，保存时逐场检查名额并报告未成功的项目。

审批结果必须以服务器成功为准；请求未完成时按钮显示“确认中”，不提前让名单增加。

### 5.4 客户档案

搜索和近期客户优先；不要默认在手机加载几百名客户。档案分为资料、固定安排、参与记录。姓名旁显示稳定身份编号；联系方式与家庭关联协助辨认同名客户。

月付／年付／私人／单次为可编辑的客户标签；付款状态、有效期和实际安排分别展示。归档动作说明会保留历史，恢复入口位于归档客户筛选中。

归档前列出未来已安排的课程，让员工明确处理未来安排；不能在客人不知情时让已确认课程悄悄消失。

### 5.5 固定重复安排

步骤：选择客户 → 选择课程与每周日期 → 起止日期 → 预览将加入的场次 → 保存。

预览包含人数、日期范围、遇到满额或停课的日期。修改时明确选择“只改这一次”或“从某日期起修改未来安排”，历史不参与修改。

单日请假、暂停和移除作为例外保存；自动生成名单时尊重例外。没有结束日期时要求员工明确选择持续安排，并提供套餐到期提醒。

### 5.6 公开报名页

手机采用短流程，最多三步：选场次 → 资料 → 核对。入口可预选明天，但允许返回修改；日期、时间、地点、需确认说明清楚显示。

收集姓名、一种联系方式和必要备注。每位参加者有自己的姓名；替多人报名必须逐个填写，不能把一个“人数”直接变成多位无名成员。

表单有真实标签、输入格式提示、键盘适配和就地错误说明。提交中防止重复点击；失败保留已填内容。提交成功显示“报名已收到，等待确认”，不能显示“预约成功”或“已加入名单”。

成功页提供报名查询链接、保存方式和当前申请摘要。已满、截止、停课分别解释原因；可候补时按钮写“申请候补”。

### 5.7 报名结果页

页面只展示该申请：醒目的状态、完整课程信息、申请人以及下一步。状态包括待确认、已确认、候补、未通过和已取消。

已确认后展示到场说明。客人可以申请改期或取消；后台处理前显示申请中，并保留原已确认安排。旧链接仍能查看处理后的结果，不因状态变化丢失。

### 5.8 现场签到

顶部固定日期、时间与场次，允许切换当天其他场次，但不能误切未来日期签到。列表提供姓名搜索和大触控区；签到按钮至少 48px，状态同时用文字和形状表达。

点击本人 → 确认操作 → 签名或直接确认（按场次设置）→ 成功反馈 → 返回名单。签名提交失败时保留笔迹供重试。成功后姓名状态变化、计数更新，焦点留在合理位置。

公开签到页不展示付款、电话、其他人的历史签名；查看自己的签名或记录需要额外授权。现场临时加人由员工处理。

### 5.9 历史与变更

日期历史显示当时正式名单、到场记录、请假／未到标记和调整原因。客户历史可以按课程筛选。

没有签到并不自动等于未到；员工核对后确认。历史更正保留操作者、时间、原值和原因；修改未来安排不会改变过去。

## 6. 视觉系统

| 角色 | 建议设计 |
|---|---|
| 导航与品牌 | 现有深绿 #0a1a0f，搭配清晰白字 |
| 主要操作 | 现有荧光绿 #00e85c，配深色文字；不使用低对比白字 |
| 内容背景 | 保留浅灰绿底与白色工作区域 |
| 正文 | 接近黑色；次级文字使用可读的深灰，正文对比至少 4.5:1 |
| 状态 | 绿色已确认、琥珀待确认、灰色取消；全部同时有文字，拒绝或错误用红色 |
| 字体 | 沿用 Plus Jakarta Sans / Noto Sans TC；Barlow Condensed 仅用于少量标题和数字 |
| 布局 | 手机一列、电脑名单与详情并列；行列表优先，避免多层卡片 |
| 控件 | 圆角 12–16px，统一线条图标，触控区至少 44px，主要签到操作至少 48px |

后台主要使用受控的品牌色；客人页面可增加更鲜明的课程标题与留白，仍优先快速填写。示例资料均为虚构。

## 7. 动效与流动感

| 交互 | 动效 | 建议时长与约束 |
|---|---|---|
| 按钮按下 | 轻微压下，颜色即时反馈 | 100–120ms，不移动其他内容 |
| 日期切换 | 选中底板连续滑动，名单短距离交叉淡入 | 180–220ms；不让整页来回滑动 |
| 场次切换 | 时间和人数保留位置，内容区域平滑切换 | 180–220ms |
| 批准报名（核心动效） | 成功后该申请收拢；正式名单新增行短暂高亮；人数同步变化 | 约 250–320ms，只有服务器成功后执行 |
| 拒绝／候补 | 行内状态更新并折叠已处理详情 | 180–220ms，不使用晃动或飞走动画 |
| 客户详情 | 电脑右侧面板展开，手机底部抽屉上推 | 220–280ms；管理键盘焦点，关闭后返回原行 |
| 固定安排预览 | 选中星期反馈，受影响日期连续高亮 | 150–200ms；没有无限闪烁 |
| 报名步骤 | 相邻步骤轻微位移，进度标记同步推进 | 180–220ms；返回时保留资料 |
| 报名提交成功 | 状态标记出现，摘要展开 | 200–250ms；文案为等待确认 |
| 签到成功 | 勾选标记描画、状态底色变化、人数更新 | 220–300ms；高频使用不弹彩纸 |
| 加载／重试 | 固定高度的占位，内容到达后淡入 | 150ms；不因加载导致按钮跳位 |

主要“流动”来自审批到名单、日期到场次、选择到详情的连续关系。后台不做开屏表演，不加入持续漂浮的数字、粒子或背景循环。支持减少动态效果模式，关闭大幅位移，以即时状态变化或短淡入替代。

桌面可选拖动改期，但手机和键盘始终提供“移动到…”操作；拖动不是唯一完成任务的方式，放下后也需要服务器确认。

## 8. 全部状态与异常

| 状态种类 | 示例 | 表达的事情 |
|---|---|---|
| 场次 | 可报名／已截止／已停课／已结束 | 这堂课是否开放 |
| 报名 | 待确认／已批准／候补／未通过／已取消 | 客人的申请处理进度 |
| 名单与出席 | 已安排／已到／已离开／请假／未到 | 当天是否应来、是否实际到场 |
| 付款 | 待付／已付／套餐内／无需付款 | 费用是否处理 |

同一客户可以同时显示“报名已批准、当天未签到、待付款”；不能用一个绿色“成功”代替全部状态。

- 默认、悬停、键盘焦点、按下、禁用、处理中、失败和成功都定义一致反馈。
- 空名单、无场次、暂无申请、满额、报名截止、停课、客户已归档分别提供准确说明。
- 姓名相同不自动关联；家庭共用电话时提示员工核对。相同客户同场次只存在一个有效位置。
- 网络断开时展示上次同步时间；管理写入必须明确失败，不能假装已经保存。恢复后可重试且不会重复批准。
- 两名员工同时处理同一申请或最后一个位置时，后保存的一方看到最新结果；不超额、不重复加人。
- 管理解锁到期时保留尚未提交的编辑内容供重新验证；不把敏感客户资料永久存到公开设备的本地存储。
- 移除名单、取消课程和更正历史有明确影响说明。已签到名单不允许悄悄消失。
- 所有日期按澳门 UTC+8；完整日期出现在确认、改期和分享摘要中。

## 9. 数据与权限蓝图（供实施使用）

客户身份、场次、固定安排、单日例外、报名申请、正式名单位置、签到事件和操作日志分别保存。正式名单不能用全体客户列表直接替代。

批准申请、核对名额、建立或关联客户、加入名单和登记操作应作为一次完整操作；任一步失败不能留下“已批准但未入名单”的状态。重复安排生成应幂等并尊重单日例外。

现有共享管理密码只能可靠记录操作时间与会话，不能证明具体是哪位员工。若要按姓名追溯操作者，应接入独立员工账号；实施时不得把共享密码日志包装成个人审计。

报名、结果查询和现场签到分别使用范围有限的链接授权；现有 teamId 链接不能自动视为所有未来场次的管理权限。公开签名查看、付款查看和跨队伍枚举应拒绝。需要在实施时进一步分拆当前公开 status/history 接口的数据字段。

旧签到记录没有新场次信息时保留在旧历史中，不根据姓名或时间随意猜测场次。新功能以新增字段和实体演进，迁移必须先验证现有数据。

## 10. 实施顺序与交付验收

1. 完成已有安全上线事项，补全公开签到、查询与管理权限的边界。
2. 建立场次、每日名单和固定安排；先让后台排每天名单顺畅。
3. 加入公开报名、查询页和后台审批；验证审批到名单完整闭环。
4. 接入场次签到、历史快照、改期和取消；验证旧历史保留。
5. 实现上述动效、手机适配、键盘操作和失败恢复；最后再接自动通知及扩展统计。

验收必须覆盖：固定名单生成与单日例外、待确认不进入现场名单、同场次重复报名、两人同时审批、满额候补、报名截止、停课、管理五分钟到期、网络失败重试、历史不被未来安排重写，以及公开链接无法访问管理与敏感资料。

## 11. 视觉确认后再实施

本次交付是完整流程、页面与交互规格，以及两种高保真视觉方向图。推荐 A 为主工作台、B 为周排期视图；两者可以组合。

需要用户确认主要布局和设备使用偏好后，再进入可点击原型和生产代码实施。视觉图中的文字、日期和人数是示例，最终以可访问、可操作、真实数据驱动的页面为准。
