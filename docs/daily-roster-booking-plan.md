# PRIMETIME 每日名单与报名确认流程

策划日期：2026-10-12。此文件是功能策划，不表示功能已实现或上线。

## 已确认的需求

- 每天的名单可以不同，由后台决定。
- 月付、年付、私人客户由员工在后台安排，可以设置固定重复安排，也可以单独调整某一天。
- 临时客人通过公开链接提交报名，必须由后台确认后才进入正式名单。
- 拿到对应签到链接的人可以签到，无需管理密码；管理操作需要服务器验证，解锁五分钟。
- 成员身份、付款状态、报名状态、当天到场状态分别保存。
- 已有成员和历史记录继续保留。

## 完整业务流程

### 1. 员工安排课程与固定客户

员工先建立日期和场次，例如“10 月 13 日，晚上 7 点，团体训练”。场次包含地点、负责人、可选人数上限和报名截止时间。私人训练使用同一套流程，但默认不开放公开报名。

在后台选择客户后，可以“只加入这一天”，或设置“每周一、三、五，持续到指定日期”。月付和年付标签帮助员工判断资格，真正决定名单的是员工保存的安排。有效期将到时先提醒员工，避免系统未经确认取消已经安排好的课程。

### 2. 系统准备每日名单

系统按固定安排生成未来名单，员工可以提前查看和修改。建议提前准备未来 30 天，并在查看尚未生成的日期时自动补齐；重复执行不会重复加人，也不会覆盖员工的单日调整。

每个客户在同一场次只占一个位置。员工从某一天移除他，不会删除客户，也不会在下一次自动生成时把他重新加回来。停止重复安排只影响指定日期之后的场次。

### 3. 临时客人提交报名

公开报名页只显示允许报名的日期和场次。默认突出“明天”，同时明确显示完整日期、时间、地点和“需后台确认”。

客人填写姓名、联系方式、人数和必要备注，提交后显示“已收到报名，等待确认”。报名会得到独立查询链接，客人可以查看自己的处理结果；该链接不展示其他客户的姓名、联系方式或签名。

首次版本建议每份报名只对应一位参加者；若需要替多人报名，应为每位参加者分别填写姓名，而不是仅填写一个人数。

### 4. 员工处理待确认报名

后台显示待处理数量，按日期和场次排列。每条申请显示姓名、联系方式、报名时间、备注、该场次已确认人数和可用位置。

员工可以批准、拒绝、改到其他场次或放入候补。批准时再次检查是否重复和是否满额；多人同时审批也不能超过上限。批准成功后才加入正式名单。

付款另行标记为“已付／待付／套餐内／无需付款”。批准报名不等于收到付款。疑似现有客户的申请可以提示员工关联，但不能仅凭同名自动合并。

### 5. 客人查看确认结果

查询页显示“待确认／已确认／候补／未通过／已取消”，确认后列出日期、场次、地点和到场说明。

第一阶段通过查询链接查看结果，员工可复制确认信息发送给客人。自动邮件、短信或 WhatsApp 通知作为后续接入项；未连接通知渠道前不声称已发送。通知失败不撤销已成功的审批。

改期和取消先作为申请提交给后台；已经确认的客人不能自己修改后台状态。员工操作后保留变更记录。

### 6. 当天签到与课后记录

现场默认打开今天，选择场次后只显示该场次正式名单。待确认报名不出现在签到名单中。已经批准的临时客和固定客户都可以通过该场次的签到链接签到。

现场临时到访者由员工补进当天名单，再签到。签到页显示应到、已到、未到、已离开人数。结束后员工可标记请假或未到，不能仅因忘记签到就自动认定客人未到。

当天安排、实际签到、签名和变更记录保存为历史。修改未来安排、修改会员标签或归档成员，都不会重写历史。

## 页面结构与推荐交互

| 页面 | 最重要的内容 | 主要操作 |
|---|---|---|
| 后台每日名单 | 日期、场次、已确认名单、待确认数量、人数上限 | 加人、单日调整、打开现场签到 |
| 待确认报名 | 日期、场次、申请人、联系方式、剩余位置 | 批准、拒绝、候补、改期 |
| 客户与固定安排 | 客户资料、付款标签、有效期、重复安排 | 单次安排、按周重复、暂停未来安排 |
| 公开报名页 | 可报名日期、场次时间地点、确认说明 | 提交报名 |
| 报名结果页 | 自己的报名状态、确认后的到场说明 | 查询、提交改期或取消申请 |
| 现场签到页 | 当前场次正式名单、到场状态 | 签到、签退 |

后台默认“今天／明天／选日期”，每日名单采用可快速扫描的行列表；现场沿用现有大按钮签到卡片。状态必须同时写文字，避免只靠颜色判断。保留 PRIMETIME 已有绿色品牌、中文与英文支持。

## 需要处理的例外

- 同一联系方式、同一场次重复提交：提示已有申请并允许查看状态，不重复占位。
- 同名不同人：不自动合并；家庭共用联系方式时允许员工确认关联。
- 已在正式名单又报名：提示已安排；疑似匹配交由员工确认。
- 满额：可申请候补，待确认与候补都不计入正式人数；批准时必须重新核对人数。
- 客人修改已确认申请：变成改期申请，原安排在员工处理前保留。
- 停课：员工取消整个场次，保留原名单及原因；阻止继续报名和签到。
- 已经签到后移除名单：不能默默抹去记录，要求员工处理并留下原因。
- 固定名单生成失败：显示生成状态和重试入口；手动补人仍可使用。
- 所有业务日期按澳门／香港时间 UTC+8 处理。

## 链接与权限

报名链接、报名查询链接、现场签到链接、管理页各有独立权限。

公开报名只能新建待确认申请，不能直接增加正式名单、批准申请或查看全部客户。报名结果链接只允许查看对应申请；现场签到链接只允许处理对应场次的到场记录。员工管理操作保留五分钟服务器会话。

新公开报名功能上线前，应先完成现有服务器密钥配置、部署验证和 RLS 切换，详见 security-rollout.md。

## GitHub 参考与采用方式

### Cal.diy / Cal.com：预约确认

- 仓库：https://github.com/calcom/cal.diy
- 参考内容：申请、确认、拒绝、改期的状态和页面分工。
- 应用方式：客人提交后明确显示等待确认，批准按钮只出现在员工后台。
- 核实依据：官方仓库及确认权限相关问题 https://github.com/calcom/cal.diy/issues/18697 。
- 官方仓库目前明确建议 Cal.diy 用于个人、非生产场景；这里作为流程参考，最终功能在现有 check-in 项目中实现。

### Easy!Appointments：日期与预约管理

- 仓库：https://github.com/alextselegidis/easyappointments
- 界面截图：https://github.com/alextselegidis/easyappointments/blob/main/screenshot.png
- 参考内容：预约与客户管理、工作安排和报名规则。
- 应用方式：后台按日期和场次组织名单；临时申请用行列表处理；私人客户可以使用场次与负责人安排。
- 核实依据：官方 README https://github.com/alextselegidis/easyappointments/blob/main/README.md 。

### LibreBooking：重复安排与日期例外

- 仓库：https://github.com/LibreBooking/librebooking
- 参考内容：重复预约、审批、候补、签到时间和公开查看权限的分别设置。
- 应用方式：固定客户可批量安排，员工可以仅修改一次或修改未来安排；公开客人不能取得管理权限。
- 核实依据：官方配置 https://github.com/LibreBooking/librebooking/blob/develop/.env.example 及更新记录 https://github.com/LibreBooking/librebooking/blob/develop/CHANGELOG.md 。

## 分阶段落地与验收

1. 完成已有安全改动上线与验证。
2. 增加日期／场次、每日名单、固定重复安排、单日例外和历史保存。
3. 增加公开报名、查询页、后台审批、重复检查及名额控制。
4. 接入通知渠道，增加候补递补和后续统计。

验收例子：明天有 12 位后台已安排客户，收到 3 份临时报名时仍显示正式名单 12 人、待确认 3 人。员工批准其中 2 人后，正式名单变为 14 人；第三位未批准的人无法进入签到名单。后天使用后天的安排重新生成名单，不会把明天的临时客自动延续过去。
